===============================================================================
3.4. IMPLEMENTACIÓN DEL SISTEMA
===============================================================================

El presente capítulo describe el entorno tecnológico, el proceso de despliegue 
y las evidencias de funcionamiento del Sistema Online de Elecciones Electorales 
con Autenticación Facial (UPEA Vota). Se detallan las plataformas, herramientas, 
comandos y configuraciones utilizadas para llevar el sistema desde el entorno 
de desarrollo hasta un ambiente de producción accesible desde internet.


-------------------------------------------------------------------------------
3.4.1. AMBIENTE DE IMPLEMENTACIÓN
-------------------------------------------------------------------------------

3.4.1.1. Arquitectura General

El sistema sigue una arquitectura de tres capas desacopladas:

  Frontend (React + Vite)  ──HTTP──>  Backend (FastAPI)  ──SDK──>  Supabase
                                                                       │
                                                                  ┌─────┴─────┐
                                                                  │ PostgreSQL │
                                                                  │ Storage    │
                                                                  │ Auth       │
                                                                  └───────────┘

Cada capa se despliega en una plataforma independiente y se comunica 
exclusivamente a través de APIs REST con autenticación JWT.


3.4.1.2. Plataformas de Despliegue

  ┌────────────┬────────────────────┬──────────────────────────────────────┐
  │ Componente │ Plataforma         │ Plan                                 │

Región de todos los servicios: South America (São Paulo), para minimizar 
latencia en el contexto universitario boliviano.

3.4.1.4. Base de Datos

Plataforma: Supabase (PostgreSQL 15+ administrado).
Esquema: definido en supabase_schema.sql (234 líneas) con 8 tablas:

  Tabla               │ Columnas principales
  ────────────────────┼────────────────────────────────────────────────
  profiles            │ id, name, last_name, reg_univ, id_card, email,
                      │ role (admin|student), career, photo_url,
                      │ password_changed, session_token, is_active, created_at
  elections           │ id, title, description, start_date, end_date,
                      │ status (active|inactive|closed), type, created_at
  categories          │ id, name, election_id (FK), created_at
  candidates          │ id, name, description, photo_url, video_url,
                      │ category_id (FK), career, created_at
  face_embeddings     │ id, user_id (FK), embedding (FLOAT8[]), created_at
  votes               │ id, user_id (FK), election_id (FK), category_id (FK),
                      │ candidate_id (FK), created_at
  audit_logs          │ id, usuario, rol, accion, detalle, ip,
                      │ resultado (exito|error), created_at
  password_reset_codes│ id, email, code_hash, expires_at, used, created_at

Además incluye:
  - Trigger on_auth_user_created: crea automáticamente un perfil en 
    public.profiles cuando un usuario se registra en auth.users.
  - Vista vote_results: agregación de votos por candidato/categoría/elección.
  - Índices: en reg_univ, election_id, category_id, candidate_id, 
    audit_logs (acción, usuario, fecha).
  - Buckets de Storage: photos-estudiantes (público), candidates (público).
  - Políticas RLS: control de acceso a nivel de fila para cada tabla.

    - supabase_admin (service role) — para operaciones administrativas 
      que requieren bypass de RLS.

  Frontend: las variables VITE_* se inyectan en tiempo de construcción 
  (build time) por Vite, según archivo vite.config.ts.

-------------------------------------------------------------------------------
3.4.2. SIMULACIÓN DE IMPLEMENTACIÓN
-------------------------------------------------------------------------------

3.4.2.1. Preparación del Repositorio

Paso 1: Inicializar Git y subir el código a GitHub.

  git init
  git add .
  git commit -m "Inicializar proyecto UPEA Vota"
  git branch -M main
  git remote add origin https://github.com/tu-usuario/fronted_votacion.git
  git push -u origin main


3.4.2.2. Configuración de Supabase (Base de Datos)

Paso 2: Crear un proyecto en Supabase.

  1. Ingresar a https://supabase.com e iniciar sesión con GitHub.
  2. Crear nuevo proyecto con nombre "upea-vota-produccion".
  3. Establecer contraseña segura para la base de datos.
  4. Seleccionar región "South America (São Paulo)".
  5. Esperar 2-3 minutos mientras se aprovisiona la instancia.

Paso 3: Obtener credenciales de API.

  En Supabase Dashboard → Project Settings → API:
    - Project URL → SUPABASE_URL
    - anon public → SUPABASE_KEY
    - service_role (secreta) → SUPABASE_SERVICE_ROLE_KEY

Paso 4: Ejecutar el esquema de base de datos.

  1. Abrir Supabase Dashboard → SQL Editor → New query.
  2. Copiar el contenido completo de supabase_schema.sql (234 líneas).
  3. Ejecutar la consulta. Verificar que no haya errores.
  4. Confirmar en Storage que existan los buckets:
     - photos-estudiantes (público)
     - candidates (público)

  El script crea automáticamente las 8 tablas, el trigger de creación 
  de perfiles, los índices, las políticas RLS, la vista vote_results 
  y los buckets de almacenamiento.

Paso 5: Configurar Google reCAPTCHA v2.

  1. Ingresar a https://www.google.com/recaptcha/admin.
  2. Crear nueva clave tipo "reCAPTCHA v2" → "No soy un robot".
  3. Agregar dominios: localhost, el frontend de Vercel y el backend de Render.
  4. Copiar Site Key → VITE_RECAPTCHA_SITE_KEY (frontend).
  5. Copiar Secret Key → RECAPTCHA_SECRET_KEY (backend).


3.4.2.3. Despliegue del Backend en Render

Paso 6: Crear el Web Service.

  1. Ingresar a https://render.com e iniciar sesión con GitHub.
  2. Hacer clic en "New +" → "Web Service".
  3. Conectar el repositorio de GitHub (fronted_votacion).
  4. Configurar los parámetros del servicio:

     ┌────────────────────┬────────────────────────────────────────────────┐
     │ Parámetro          │ Valor                                          │
     ├────────────────────┼────────────────────────────────────────────────┤
     │ Name               │ upea-vota-api                                  │
     │ Region             │ South America (São Paulo)                      │
     │ Branch             │ main                                           │
     │ Runtime            │ Python 3                                       │
     │ Build Command      │ pip install -r requirements.txt &&             │
     │                    │ pip install face_recognition==1.3.0 --no-deps   │
     │ Start Command      │ uvicorn app.main:app --host 0.0.0.0            │
     │                    │ --port $PORT --forwarded-allow-ips '*'          │
     │ Plan               │ Free                                           │
     └────────────────────┴────────────────────────────────────────────────┘

  5. En la sección "Advanced" → "Environment Variables", agregar:

     SUPABASE_URL, SUPABASE_KEY, SUPABASE_SERVICE_ROLE_KEY,
     JWT_SECRET, CORS_ORIGINS, RECAPTCHA_SECRET_KEY,
     RECAPTCHA_SKIP_VERIFICATION=false, FACE_MATCH_THRESHOLD=0.55,
     SMTP_SERVER, SMTP_PORT=587, SMTP_USER, SMTP_PASSWORD,
     SMTP_FROM_EMAIL (opcionales).

  6. Hacer clic en "Deploy Web Service".

  Render ejecuta el build command, que instala las dependencias Python 
  (incluyendo dlib-bin, face_recognition y opencv), y luego inicia 
  el servidor con uvicorn.

  Problema encontrado: La compilación de dlib desde fuente excede el 
  límite de 15 minutos del plan gratuito de Render.
  
  Solución implementada: Se usa dlib-bin (wheel precompilado) en lugar 
  de dlib (fuente), y face_recognition se instala con --no-deps para 
  evitar que arrastre el dlib original. Esto se documenta tanto en 
  requirements.txt como en el Build Command de render.yaml.

  Al completar el despliegue, la API responde en:
    https://upea-vota-api.onrender.com/
  
  Con respuesta esperada:
    {"message": "Bienvenido a la API de UPEA Vota", 
     "status": "online", 
     "version": "1.0.0"}

  La documentación interactiva de la API está disponible en:
    https://upea-vota-api.onrender.com/docs


3.4.2.4. Despliegue del Frontend en Vercel

Paso 7: Crear el proyecto en Vercel.

  1. Ingresar a https://vercel.com e iniciar sesión con GitHub.
  2. Hacer clic en "Add New..." → "Project".
  3. Conectar el repositorio de GitHub (fronted_votacion).
  4. Vercel detecta automáticamente Vite como framework.
  5. Configurar:

     ┌────────────────────┬────────────────────────────────────────────────┐
     │ Parámetro          │ Valor                                          │
     ├────────────────────┼────────────────────────────────────────────────┤
     │ Framework Preset   │ Vite (automático)                              │
     │ Build Command      │ npm run build                                  │
     │ Output Directory   │ dist                                           │
     │ Root Directory     │ ./ (raíz del repositorio)                      │
     └────────────────────┴────────────────────────────────────────────────┘

  6. En "Environment Variables", agregar:
     VITE_API_URL = https://upea-vota-api.onrender.com/api/v1
     VITE_RECAPTCHA_SITE_KEY = (site key de Google)

  7. Hacer clic en "Deploy".

  Vercel ejecuta npm install y npm run build (tsc -b && vite build), 
  generando el directorio dist/ con los archivos estáticos optimizados.

  El archivo vercel.json incluye rewrites para SPA routing:
    { "source": "/(.*)", "destination": "/index.html" }

  Al completar, el frontend está disponible en:
    https://fronted-votacion.vercel.app

  Problema encontrado: Las rutas directas (ej. /login, /admin/dashboard) 
  devolvían 404 porque Vercel buscaba archivos físicos.
  
  Solución: Se agregó vercel.json con la regla de rewrite que redirige 
  todas las rutas a index.html, permitiendo que React Router maneje 
  la navegación del lado del cliente (SPA routing).


3.4.2.5. Creación del Administrador Inicial

Paso 8: Registrar el primer usuario y promoverlo a administrador.

  1. Ingresar al frontend (https://fronted-votacion.vercel.app/register).
  2. Completar el formulario de registro con datos reales.
  3. Escanear el rostro (obligatorio para la creación de cuenta).
  4. Iniciar sesión con el RU y CI registrados.
  5. En Supabase SQL Editor, ejecutar:

     UPDATE public.profiles 
     SET role = 'admin' 
     WHERE reg_univ = 'TU_REGISTRO_UNIVERSITARIO';

  6. Cerrar sesión y volver a iniciar. El sistema redirige automáticamente 
     al panel de administración (/admin/dashboard).


3.4.2.6. Configuración del Pipeline CI/CD

El flujo de despliegue continuo funciona de la siguiente manera:

  ┌──────────┐    git push    ┌──────────┐    webhook    ┌──────────┐
  │ Desarrollador │ ──────────→ │  GitHub  │ ────────────→ │  Render  │
  │ (local)       │             │ (main)   │               │ (backend)│
  └──────────┘                  └──────────┘               └──────────┘
                                      │                        
                                      │ webhook                
                                      ▼                        
                                 ┌──────────┐                  
                                 │  Vercel  │                  
                                 │ (frontend)│                 
                                 └──────────┘                  

  1. El desarrollador hace commit y push a la rama main en GitHub.
  2. GitHub notifica automáticamente a Render y Vercel mediante webhooks.
  3. Render ejecuta el Build Command, instala dependencias Python y 
     despliega el nuevo backend (2-5 minutos).
  4. Vercel ejecuta npm install && npm run build, genera dist/ y 
     despliega el nuevo frontend (1-2 minutos, sin tiempo de inactividad).
  5. Si se requieren migraciones de base de datos, se ejecutan 
     manualmente en Supabase SQL Editor.

  NOTA: En Render Free, el servicio se "duerme" después de 15 minutos 
  sin actividad. La primera solicitud tras inactividad tarda 30-60 
  segundos en responder. Se recomienda configurar UptimeRobot (gratis) 
  para hacer ping cada 10 minutos al endpoint raíz de la API.

3.4.3. EVIDENCIAS DE FUNCIONAMIENTO
-------------------------------------------------------------------------------

3.4.3.1. Funcionalidades Implementadas y Verificadas

A. Registro de Usuarios
   - Formulario multi-paso (4 pasos): datos personales, requisitos 
     biométricos, captura de perfil, resumen y confirmación.
   - Captura de rostro obligatoria mediante react-webcam.
   - Validación facial en backend: detección de exactamente 1 rostro 
     usando face_recognition (HOG + SVM). Si se detectan 0 o múltiples 
     rostros, se rechaza con error 422.
   - Extracción de embedding facial (vector de 128 dimensiones) 
     almacenado en la tabla face_embeddings.
   - Creación de usuario en Supabase Auth + perfil en public.profiles.
   - Verificación: query en Supabase SELECT * FROM public.profiles 
     confirma la creación del perfil. SELECT * FROM public.face_embeddings 
     confirma el embedding.

B. Autenticación (Login)
   - Inicio de sesión con RU + CI (contraseña).
   - Verificación reCAPTCHA v2 ("No soy un robot").
   - Validación de credenciales contra Supabase Auth con sign_in_with_password.
   - Generación de token JWT (HS256, expiración 24 horas).
   - Bloqueo de cuentas deshabilitadas (is_active = false).
   - Registro en auditoría de cada intento (exitoso o fallido).
   - Verificación: Login exitoso redirige al dashboard correspondiente 
     (admin → /admin/dashboard, student → /student/dashboard).

C. Panel de Administración
   - Dashboard con estadísticas globales (total estudiantes, elecciones 
     activas, votos emitidos, tasa de participación).
   - Gestión de elecciones: CRUD completo con fechas, estado y tipo.
   - Gestión de categorías: creación y eliminación.
   - Gestión de candidatos: CRUD con foto, descripción y video.
   - Gestión de estudiantes: listado, búsqueda y eliminación.
   - Gestión de usuarios registrados: listado completo con estado 
     (activo/inactivo), toggle de activación/desactivación.
   - Panel de auditoría: registro paginado de eventos del sistema con 
     filtros por acción, rol, resultado, fecha y búsqueda general.
   - Resultados en vivo con gráficos (Recharts) y exportación.

D. Votación Electrónica
   - Flujo completo: seleccionar elección activa → categoría → candidato.
   - Verificación biométrica facial obligatoria antes de emitir el voto 
     (comparación del rostro capturado contra el embedding almacenado).
   - Control de voto único: UNIQUE(user_id, election_id, category_id) 
     evita doble votación en la misma categoría.
   - Registro en auditoría de cada voto emitido.
   - Verificación: SELECT COUNT(*) FROM votes WHERE user_id = 'X' 
     confirma un solo voto por categoría.

E. Panel del Estudiante
   - Dashboard personal con estado de votación.
   - Historial de votos emitidos.
   - Carnet de sufragio digital (PDF generado con jsPDF + QR).
   - Perfil: edición de datos y cambio de foto.
   - Cambio de contraseña.

F. Seguridad y Auditoría
   - Todas las acciones críticas se registran en audit_logs:
     registro, inicio de sesión (éxito/fallo), cambio de contraseña, 
     emisión de voto, cierre de sesión, acciones administrativas.
   - JWT con session_token: al cerrar sesión en todos los dispositivos, 
     se invalida el token regenerando el session_token en profiles.
   - Límite de tasa: máximo 3 solicitudes de recuperación de contraseña 
     por hora por email.
   - Transacciones: si falla el guardado del embedding facial después 
     de crear el usuario, se elimina el usuario (rollback).

3.4.3.3. Resultados de la Verificación Biométrica

  El modelo de reconocimiento facial (dlib HOG + SVM) genera vectores 
  de 128 dimensiones. La comparación se realiza mediante distancia 
  euclidiana con un umbral configurable (FACE_MATCH_THRESHOLD = 0.55).

  Estrategia de detección (3 intentos, definidos en 
  app/services/biometric/dlib_provider.py):

    1. HOG con padding superior 20% (mejora detección de coronilla).
    2. HOG sin padding (imagen original).
    3. Ecualización de histograma + upsampling (imágenes con baja 
       iluminación o contraste).

  Si los 3 intentos fallan, el sistema rechaza la operación. Esto 
  garantiza que ningún usuario pueda registrarse o votar sin un rostro 
  válido y detectable.

3.4.3.5. Conclusión de las Pruebas

  El sistema UPEA Vota fue implementado exitosamente en un entorno de 
  producción utilizando tecnologías modernas y de código abierto. Todas 
  las funcionalidades críticas fueron verificadas:

  - Registro biométrico con validación facial obligatoria.
  - Autenticación multifactor (credenciales + reCAPTCHA + JWT).
  - Votación electrónica con verificación biométrica en tiempo real.
  - Control de voto único a nivel de base de datos.
  - Panel administrativo completo con gestión de usuarios, elecciones, 
    candidatos y auditoría.
  - Cierre automático de elecciones vencidas.
  - Despliegue continuo mediante GitHub + Render + Vercel.
